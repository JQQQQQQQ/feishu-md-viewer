# 发布质量与 E2E 验收设计

## 1. 背景

Feishu MD Viewer 已同时支持 Chrome 浏览器扩展和 VS Code 只读预览，核心能力包括 Markdown 渲染、目录导航、表格选择与复制、表格列宽持久化、Mermaid 预览以及本地文件自动刷新。当前项目已有较完整的单元测试和若干一次性浏览器诊断脚本，但缺少统一的发布门禁、稳定的浏览器关键路径 E2E 和可重复执行的发布验收清单。

本设计的目标是建立一套“提交前可自动验证、发布前可人工复核、Chrome 与 VS Code 互不串包”的质量闭环，优先保护已有预览体验，不引入新的编辑功能。

## 2. 目标与非目标

### 2.1 目标

- 提供一个统一的 `npm run verify:release` 命令，串联测试、类型检查、两端构建和产物检查。
- 用真实浏览器覆盖本地 Markdown 预览和自动刷新主链路。
- 固化表格选择/复制、目录、主题、Mermaid 和局部刷新等高风险交互的回归场景。
- 为 VS Code 提供可重复的宿主/Webview 自动检查和人工验收清单。
- 在 CI 中执行不依赖人工操作的质量门禁。
- 检查版本号、入口文件、引用资源和扩展包内容，避免生成不可安装或串包的产物。

### 2.2 非目标

- 本阶段不恢复 Markdown 或 Mermaid 编辑能力。
- 不在 CI 中自动操作用户本机的真实 VS Code 界面。
- 不把一次性诊断脚本全部改写为 E2E；只有稳定、可重复的主流程才进入门禁。
- 不在本阶段重构 Markdown 解析器或表格组件内部实现。
- 不强制引入远程服务、账号认证或在线仓库存储。

## 3. 整体架构

```text
                ┌─────────────────────────┐
                │   npm run verify:release │
                └────────────┬────────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
        ▼                    ▼                    ▼
  单元/组件测试          构建与类型检查        产物完整性检查
        │                    │                    │
        └──────────────┬─────┴──────────────┬─────┘
                       │                    │
                       ▼                    ▼
              浏览器关键路径 E2E      VS Code 宿主/Webview 校验
                       │                    │
                       └──────────┬─────────┘
                                  ▼
                         发布验收报告/CI 结果
```

质量层分为三类：

1. **逻辑回归层**：继续使用 Vitest，验证解析、状态、表格选择、刷新监控和 VS Code Provider 等纯逻辑。
2. **真实界面层**：使用浏览器 E2E 验证真实 DOM、滚动、剪贴板触发、文件变化和扩展注入行为。
3. **发布产物层**：使用 Node 脚本检查构建目录、资源引用、版本号和 VSIX 内容，避免“测试通过但安装包不可用”。

## 4. 统一发布门禁

### 4.1 命令编排

新增脚本：

```text
scripts/release/verify-release.mjs
```

新增 npm 命令：

```json
{
  "verify:release": "node scripts/release/verify-release.mjs"
}
```

门禁按以下顺序执行，并在任一步失败时停止：

1. `TMPDIR=/tmp npm test -- --run`
2. `npm run typecheck`
3. `npm run build`
4. `npm run build:vscode`
5. `npm run verify:vscode`
6. 发布版本和产物检查
7. 浏览器 E2E（本地环境具备浏览器运行条件时执行）

脚本输出每个阶段的开始、结束、耗时和退出码；失败时保留失败阶段和原始日志，不把后续阶段的成功误报成整体成功。

### 4.2 产物检查

新增脚本：

```text
scripts/release/check-artifacts.mjs
```

检查内容：

- 根目录 `dist/manifest.json` 存在且 JSON 有效。
- Chrome Manifest 的入口、图标和 Service Worker 引用的文件真实存在。
- VS Code `vscode-extension/out/extension.js` 存在。
- VS Code Webview 的 `index.html`、JavaScript 和 CSS 资源存在，HTML 引用路径可解析。
- Chrome 构建入口不包含 VS Code API 导入。
- VS Code Webview 构建入口不包含 `chrome.*` 运行时依赖。
- Chrome Manifest、根 `package.json` 和 VS Code `package.json` 的版本号格式有效；Chrome 与 VS Code 可以使用独立版本号。
- 生成的 VSIX 文件存在，且压缩包内包含宿主入口、Webview 入口和必要资源。

版本号不要求每次提交都自动递增，但发布检查必须阻止空版本、非法版本，以及同一平台的源配置、构建产物和发布包版本不一致。发布报告同时记录 Chrome 和 VS Code 的版本号。

## 5. 浏览器 E2E 设计

### 5.1 测试工具与 Fixture

新增浏览器测试目录：

```text
tests/e2e/browser/
tests/e2e/fixtures/
```

新增综合 Fixture：

```text
tests/e2e/fixtures/all-markdown-features.md
```

Fixture 必须包含：

- 文档主标题、二级和三级标题
- 普通段落、粗体、斜体、删除线、链接和内联代码
- 有序列表、无序列表、任务列表
- 引用和 Callout
- 普通代码块和多语言代码块
- 图片
- 普通表格、宽表格和带表头表格
- 至少一个有效 Mermaid 图和一个无效 Mermaid 图
- 足够长的正文，用于滚动和标题定位验证

浏览器 E2E 使用 Playwright 或项目中已经存在且可在 CI 安装的等价浏览器驱动。测试必须通过稳定的 data 属性、ARIA 名称或语义角色定位，不依赖脆弱的 CSS 层级选择器。

### 5.2 主流程场景

#### 本地文件预览

- 打开 Fixture 对应的本地 Markdown 文件。
- 验证原始 `<pre>` 被隐藏，Feishu 预览根节点存在。
- 验证正文、目录、表格、代码块、引用、图片和 Mermaid 区块可见。

#### 自动刷新

- 在选项页选择“自动刷新”。
- 打开本地 Markdown 文件并记录正文滚动位置和表格滚动位置。
- 修改 Fixture 文件内容并保存。
- 在检测周期内验证正文局部更新。
- 验证不出现“立即刷新”按钮。
- 验证页面和表格滚动位置没有被重置。
- 验证同一次文件变化不会重复刷新。

#### 手动刷新

- 切换为“提示后手动刷新”。
- 修改文件并保存。
- 验证出现更新提示。
- 点击一次“立即刷新”。
- 验证正文更新、提示消失且不会重复出现。
- 模拟空响应或临时读取失败，验证现有正文不会被清空。

#### 表格

- 点击单元格后验证单元格高亮。
- 点击上边框选择整列、点击左边框选择整行。
- 拖拽列选择或行选择到可视区域外，验证滚动和选择范围同步。
- 框选单元格内部分文字，验证不被 Excel 式选区遮挡。
- 复制单元格区域，验证剪贴板同时包含 TSV 和可识别的 HTML 表格结构。
- 拖动列宽后刷新或重新打开，验证列宽保持。

#### Mermaid

- 有效图显示图表而不是源码。
- 打开预览弹窗后，滚轮默认滚动图表视口，不缩放文档页面。
- 图表在预览框中居中。
- 无效语法显示错误降级状态，不影响其他 Markdown 内容。
- 浅色和深色主题下连线、节点、文字和背景均可读。

#### 目录和布局

- 点击目录项后标题定位准确。
- 目录折叠不改变正文居中布局。
- 宽表横向滚动时，目录自动收起/恢复逻辑不阻塞正文操作。
- 切换标签页回来后不出现内容消失、目录闪烁或回到顶部。

### 5.3 E2E 稳定性规则

- 文件变化测试使用临时目录和测试副本，不修改仓库中的 `test-e2e.md`。
- 每个测试结束清理临时文件、监听器和浏览器上下文。
- 自动刷新等待使用明确的轮询断言，不使用固定长 `sleep` 作为唯一同步方式。
- 失败时保存截图、页面 HTML 和控制台日志。
- E2E 默认串行执行涉及同一文件的场景，避免文件写入互相干扰。

## 6. VS Code 验收设计

### 6.1 自动检查

继续使用现有 VS Code Provider、Webview 消息和构建隔离测试，并将以下检查纳入统一发布门禁：

- Provider 可以打开 Markdown 文档并推送内容。
- 文档外部更新后能向 Webview 推送最新内容。
- 主题变化消息可以到达 Webview。
- Webview 不导入 VS Code API。
- 构建资源引用路径全部可解析。
- VSIX 包包含正确版本和必要文件。

### 6.2 人工验收清单

在 Windows 原生 VS Code 中使用干净 Profile 安装 VSIX，验收：

1. 双击 `.md` 默认进入 Feishu 只读预览。
2. 修改并保存 Markdown 后预览更新。
3. 用外部编辑器修改文件后预览更新。
4. 浅色、深色、高对比主题显示正常。
5. 表格选择、部分文字复制和列宽持久化正常。
6. Mermaid 正常图和错误图均有合理显示。
7. `Reopen Editor With…` 可以回到 VS Code 原生编辑器。
8. 预览不会修改源文件。
9. 关闭并重新打开 VS Code 后全局预览设置保留。

人工验收结果记录到：

```text
docs/release-acceptance.md
```

每项记录环境、步骤、预期、实际结果和截图/日志路径；“自动测试通过”不能代替真实 VS Code 手工验收。

## 7. CI 设计

新增：

```text
.github/workflows/ci.yml
```

建议矩阵：

- Node.js 20
- Node.js 22

CI 阶段：

1. 安装依赖并缓存 pnpm/npm 依赖。
2. 执行全量 Vitest。
3. 执行类型检查。
4. 构建 Chrome 和 VS Code。
5. 检查构建产物。
6. 在具备浏览器依赖时执行浏览器 E2E。
7. 上传失败截图、HTML、日志和构建包作为 Artifact。

由于真实 VS Code GUI 不适合在当前 CI 中强行自动化，CI 只负责 Provider/Webview/产物自动门禁，VS Code GUI 清单保留为发布前人工检查。

## 8. 失败处理与可观测性

- 自动刷新失败时保留当前正文，并将失败状态写入可诊断日志。
- E2E 失败输出场景名称、当前 URL、页面标题和最后一次文件内容版本。
- 发布门禁失败时不生成或不标记可发布包。
- 不在生产预览页常驻调试日志；诊断信息通过测试报告和开发模式输出。
- 对 Mermaid JSDOM 的 `getBBox` 已知测试降级警告单独标记，不得掩盖真正的 E2E 失败。

## 9. 分阶段交付

### Phase 1：统一门禁和产物检查

- `verify:release`
- 版本和构建产物校验
- 规范化发布验收文档

### Phase 2：浏览器关键路径 E2E

- Fixture
- 本地文件预览
- 自动/手动刷新
- 目录、表格和 Mermaid 主流程

### Phase 3：CI 接入

- GitHub Actions
- Node 20/22 矩阵
- E2E 失败产物上传

### Phase 4：真实 VS Code 发布验收

- 干净 Profile 安装 VSIX
- 执行人工清单
- 记录版本、环境和截图

## 10. 验收标准

- `npm run verify:release` 在干净依赖环境中成功完成。
- 全量单元测试、类型检查、Chrome 构建和 VS Code 构建均为成功状态。
- 浏览器 E2E 覆盖自动刷新、手动刷新、表格复制、目录定位和 Mermaid 错误降级。
- 自动刷新不会显示手动按钮，不会清空正文，不会重置滚动位置。
- VS Code 产物检查通过，Chrome 和 VS Code 入口没有跨端 API 污染。
- VSIX 可以在 Windows 原生 VS Code 中安装并完成人工验收清单。
- CI 能在任一门禁失败时明确失败，不产生误报的绿色结果。
